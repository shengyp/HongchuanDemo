# 长尾知识补偿驱动的个性化营养食谱系统 V1.0

本系统是 Nutri20K 营养食谱任务与长尾知识补偿思路相结合的本地研究原型。页面结构参考 EduTechLLM 的登录与工作台组织方式，代码为独立实现。前端使用 Vue 3、Vite、TypeScript 和 Element Plus 多选组件；后端使用 Python 标准库和 SQLite。项目中的 `data/demo.json` 是功能演示数据，不代表 Nutri20K 正式数据，也不用于真实膳食建议。

## 功能

- 工作台：打开后直接进入体验模式，按模块导航并保存本地问答记录。账户机制的后端代码保留作以后启用。
- 智能问答：根据用户问题检索食谱和营养数据；配置本地 Ollama 后支持生成式回答。
- 数据导入：导入食材营养密度和食谱组成的 JSON 文件，或分别上传两张 CSV 表。
- 长尾分析：按食材出现频率识别低频食材，查看已观察到的共现与推断的候选关联。
- 知识补偿：以营养向量、食材类别及名称相似度查找常见食材，将其共现关系作为候选证据传递给长尾食材。
- 食谱推荐：结合每份营养值、用户偏好与排除食材进行排序，显示分数及候选关联解释。
- 食谱克数生成：选定基础食谱后调整食材克数，逐项验算六项营养约束，并明确显示是否达标。
- 数据复位：恢复内置演示数据。
- USDA 来源目录：浏览用户提供的 FoodData Central 压缩包中六项营养齐全的 Foundation Foods 食材，保留 FDC ID 与文件哈希。
- Food.com 真实食谱分析：基于用户提供的 `RAW_recipes.csv` 检索食谱、统计长尾食材和实际共现关系；不伪造缺失的食材克数。

候选关联只改变推荐排序及解释，不会修改食材营养值。当前版本使用轻量相似度算法，**没有加载 BERT 权重，也不是论文 UnKGE-BCKC 的原样复现**。

## 运行

需要 Python 3.10+、Node.js 20+、pnpm。进入 `frontend` 后安装依赖并构建：

```powershell
cd frontend
pnpm install
pnpm run build
cd ..
python app.py
```

在浏览器访问 `http://127.0.0.1:8765`，页面会直接进入体验工作台，无需注册或输入密码。体验会话和问答保存在本机 `data/app.db`。若本机的 pnpm 代理阻止 `esbuild` 安装脚本，可在确认依赖来源后允许运行该脚本。Vite 的脚本已使用 `--configLoader runner`，适配当前中文路径。已构建的 `dist/` 可直接由 Python 提供，无需运行 Node.js。

开发时分别运行 `python app.py` 和 `cd frontend; pnpm run dev`，前端 Vite 地址为 `http://127.0.0.1:5173`，`/api` 自动代理至 Python 后端。

## 营养食谱问答与模型选择

顶部“营养食谱问答”是独立模块，支持新建和切换对话。每次提问前可选择“知识检索”或已就绪的大模型；回答记录保留实际模型标记。检索到的食谱和营养值作为回答依据提供给模型，候选关联不能当作真实食谱事实。

系统会自动读取本机 Ollama /api/tags 中已安装的模型并列入选择区。启动 Ollama 并安装模型后，刷新页面或点击“刷新模型列表”即可选择。NUTRI_OLLAMA_URL 可指定 Ollama 服务地址，默认 http://127.0.0.1:11434；旧配置 NUTRI_OLLAMA_MODEL 仍可用于提示预期模型是否已安装。

其他支持 OpenAI 兼容 /chat/completions 接口的服务，可在后端用 NUTRI_LLM_PROVIDERS 配置多个模型。例如在启动后端前设置：

~~~powershell
$env:NUTRI_LLM_PROVIDERS = '[{"label":"研究模型 A","provider":"自定义服务","model":"model-a","base_url":"https://your-provider.example/v1","api_key_env":"NUTRI_PROVIDER_A_KEY"}]'
$env:NUTRI_PROVIDER_A_KEY = '你的服务端密钥'
python app.py
~~~

列表中每一项的 label 是界面名称，model 是服务接口使用的模型编号。可以添加多项，并分别指定 base_url 和 api_key_env。密钥只在后端环境变量中读取，不返回给浏览器。未配置密钥的模型会显示“不可用”；连接或调用失败会直接提示错误，不会伪装成大模型回答。知识检索始终可用。模型权重和第三方接口费用不包含在系统源码中。

## 数据格式

参见前端“数据管理”页面示例。`ingredients` 中每个食材有 `id`、`name`、可选 `category`、`per_100g`；后者必须包含能量、蛋白质、脂肪、碳水、膳食纤维和钠六项非负数值。`recipes` 中每道食谱有 `id`、`name`、正整数 `servings` 和食材 `id` 与 `grams`。食谱克数为整道食谱的克数，系统会除以份数得到每份营养值。

导入文件保存在 `data/current.json`。点击“恢复演示数据”会删除该文件。请仅导入有使用权的数据；系统不会自动从压缩包中复制或发布 Nutri20K 论文和原代码。

CSV 导入可直接使用 `templates/ingredients.csv` 和 `templates/recipe_parts.csv` 作为列名模板。前者每行一种食材，六项营养值按每 100 g 填写；后者每行一道食谱中的一种食材，`grams` 为整道菜的可食部克数，同一食谱的 `recipe_id`、`recipe_name`、`servings` 必须一致。系统会验证列名、数值、食材引用和食谱份数。来源说明写入导入数据的 `metadata.source`。**模板中的数值仅为演示值，不是正式数据。**

手头 `Nutri20K-main.zip` 包含任务样本与处理脚本，但没有可直接供本系统计算的完整每 100 g 食材营养表和食谱克数表。其 README 指出原始 USDA/FNDDS 与 Food.com 数据需要另外取得。可先从 [USDA FoodData Central 官方下载页](https://fdc.nal.usda.gov/download-datasets/)获取营养数据，再整理食谱组成和单位映射；不要把问答文本中的份量描述直接当作已核验的克数。

## 计算规则

长尾阈值为当前数据中出现过的食材频次的第 25 百分位；频次低于或等于阈值的食材标记为长尾。相似度由营养向量余弦相似度（55%）、类别一致（30%）、名称词重合（15%）组成。相似度至少为 0.65 的常见食材可提供共现候选。候选边标为 `inferred`，与真实共现边 `observed` 分开展示。

推荐分数 = 70% 营养匹配 + 30% 偏好匹配。能量、蛋白质、脂肪、碳水按目标相对偏差计算；纤维按下限、钠按上限计算。排除食材是硬条件。推荐结果中的候选关联只作为弱偏好证据。

食谱克数生成基于现有食谱模板进行确定性坐标搜索，在各食材原始克数的 20%–300% 范围内调整（另有 1–600 g 边界）。优化目标是六项营养相对偏差的平方均值，并轻微惩罚过大的克数调整。输出先四舍五入到 0.1 g，再重新计算营养值与偏差。能量、蛋白质、脂肪、碳水相对偏差须在 5% 内；纤维不能低于目标 5% 以上，钠不能高于上限 5% 以上。若无法全部满足，系统仍显示最接近方案并标记“未全部达标”。这是参考 Nutri20K 数量优化任务设计的独立实现，不宣称复现其论文算法或实验指标。

## 目录

- `app.py`：本地 HTTP 服务与接口。
- `auth.py`：本地账户、会话与问答记录。
- `assistant_service.py`：知识检索与可选 Ollama 接入。
- `core.py`：数据验证、长尾统计、补偿关联及推荐计算。
- `generator.py`：食谱克数优化与目标验算。
- `csv_import.py`、`templates/`：双表 CSV 导入与列名模板。
- `tools/convert_fdc.py`、`data/fdc_foundation_complete.json`：USDA 数据筛选与可追溯来源目录，规则见 `docs/USDA数据接入记录.md`。
- `tools/convert_foodcom.py`、`foodcom_service.py`、`data/foodcom.sqlite`：Food.com 食谱索引和长尾分析，规则见 `docs/Foodcom数据接入记录.md`。
- `frontend/`：Vue 3 + TypeScript 页面及 Vite 配置。
- `data/demo.json`：演示数据。
- `docs/软件设计说明书.md`、`docs/用户使用说明书.md`：软著材料草稿。

## 不确定知识数据集上传

打开“数据管理 → 不确定知识管理”，选择 CSV 或 JSON 文件，必须填写数据集名称，按需填写来源，再点击“上传并构建图谱”。数据集列表默认选中 Food.com，显示真实食谱、食材和长尾统计；点击已上传的三元组数据集，下面会切换为该数据集的节点、关系、置信度分布与明细。已上传数据集可以在列表下方重命名，不改变三元组和来源记录。已上传的三元组数据集可在确认后删除，相关三元组及关联发现任务一并删除；默认 Food.com 数据集不可删除。选中 Food.com 时，下方展示其真实食谱—食材图谱概览、食材频次统计和可检索的三元组明细；该来源没有关系置信度。Food.com 食谱索引与三元组图谱分别管理；图谱保存在本地 SQLite 数据库 data/kg.sqlite 中。

CSV 必需列为 head、relation、tail、confidence；confidence 为 0 到 1 的数字。可选列为 evidence、source、head_type、tail_type。页面可下载 CSV 模板。JSON 格式可为三元组数组，或含 triples 数组的对象，字段名与 CSV 相同。单文件最多 20 MB、10 万条记录。缺少类型时显示“未分类”，缺少单条来源时采用数据集来源。实体节点按照“名称 + 类型”去重；知识关系数即三元组数。置信度分布只描述上传数据，不代表关系已核实。

## 后续模块的数据集选择

知识图谱可视化、食谱与食材检索、食材关联发现均提供数据集选择，默认列出 Food.com，并列出数据管理中上传的知识三元组数据集。切换数据集后，图谱、检索或任务列表随所选数据源更新。Food.com 图谱展示原始食谱—食材关系，不提供置信度；在关联发现页选择 Food.com 时查看真实共现与来源食谱，预测任务仍基于上传的带置信度三元组图谱。

营养推荐、食谱克数生成、DIY 评估、营养问答及本地长尾分析使用“营养计算数据集”选择；可选演示营养数据，以及导入后出现的当前营养数据。DIY 同时单独显示默认 Food.com 食谱证据数据集。营养计算接口按选择读取对应数据，Food.com 不会被当作营养表使用。

## 知识图谱可视化

进入“知识图谱可视化 → 知识图谱可视化”，在顶部选择已上传的数据集。可按实体名称、实体类型、关系类型检索，选择 1 层或 2 层邻居；支持力导向与环形布局、缩放和重置。点击节点将其作为新的中心实体，点击关系线查看三元组的置信度、来源和原文证据。页面使用上传数据中的实际关系；为保持交互流畅，单次局部图谱最多返回 100 条关系。

## 第四模块：食材关联发现

进入“食材关联发现 → 关联发现任务”，点击“创建发现任务”，选择已上传的数据集、待预测关系和目标实体。任务结果会保存为独立快照，可在任务历史中重新查看。候选关系显示排序分数、支持它的相似实体、共同邻居、原始三元组编号、置信度、来源与原文证据。

当前采用可解释的共享邻居启发式排序：比较同类型实体在其他关系上的共同邻居，再结合其已观察目标关系的置信度生成候选；已存在的目标关系会被排除。分数用于排序，不是经过校准的概率，也不是已训练模型的输出。证据不足时明确返回空候选。预测结果只保存在任务中，不写回上传的真实三元组，也不修改营养值。

## 第五模块：DIY 食谱证据与营养评估

进入“DIY 食谱与评估 → DIY 食谱评分”，填写食材、可食部克数、份数与六项营养目标。系统使用当前营养表计算每份营养值，并在本地 Food.com 索引中检索相关真实食谱，统计食材两两共现的食谱数量与示例，分别展示“搭配证据支持分”和“营养目标匹配分”。证据支持分由已观察搭配覆盖率、共现次数及相关食谱相似度组成；它是可解释的启发式分数，不是经过校准的概率或训练模型输出。

本地食材与 Food.com 食材采用精确名称或已列明的英文别名映射；未映射食材会标明并按缺少证据处理。Food.com 只提供食谱组成依据，本页的营养值来自当前营养表。若当前营养表为功能演示数据，页面会明确提示需导入真实营养表后再用于正式分析。
